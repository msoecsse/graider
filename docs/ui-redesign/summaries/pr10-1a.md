# PR10-1a: fix the blank screen on assignment creation

## Summary

Diagnosed and fixed the white-screen crash reported against `2419cc1`, then
added the general backstop README section 2.5 already calls for (a routed
screen throwing must never blank the whole app) and the successful-confirm
test PR7-1 deferred.

**Root cause, confirmed before touching the render.** The crash is
`preview.files.map(...)` at `AssignmentSetupPage.tsx:634` throwing because
`preview.files` is `undefined` -- but the type (`AssignmentSetupPreviewResult`,
required `files`) is not the bug. Traced `previewAssignmentSetup`'s IPC
handler in `ui/electron/main.ts:616-646`:

```ts
const preview = previewAssignmentSetup(request);
if (preview.status !== "ready") return preview;
if (request.templateRepository.trim() === "") return saveAssignmentSetup(request);
```

When the (optional, explicitly "leave blank to omit" in the UI) template
repository field is blank, the **preview** channel calls `saveAssignmentSetup`
and returns its result -- `AssignmentSetupSaveResult` (`status:
"success"|"failure"`, `writtenFiles`, `diagnostics`; **no `files` field at
all**) -- mislabeled as a preview. The renderer's preview request always has
`confirmed: false` (`createRequest`, line 58), so this always hits
`saveAssignmentSetup`'s own first guard (`if (!request.confirmed) return
{status: "failure", writtenFiles: [], diagnostics: [...]}`) -- nothing is
actually written to disk on this path, but the shape returned is still wrong.
`AssignmentSetupPage.tsx`'s `handlePreview` stores this object into `preview`
state unconditionally (`setPreview(nextPreview)`), and the JSX at line 634
evaluates `preview.files.map(...)` on every render regardless of whether the
confirmation modal is open. The crash therefore happens on the very first
click of "Create assignment" whenever the template fields are left blank --
before the confirmation dialog ever appears -- which is exactly "completing
the create-assignment flow" from a hand-tester's point of view for the
simplest, most common case (no template repository).

This is an **IPC contract bug** (a preview-only channel silently switching to
a save-shaped response), not a renderer shape-guessing problem, confirmed by
reading `ui/electron/assignmentSetupService.ts`'s `previewAssignmentSetup`/
`saveAssignmentSetup` directly -- the already-computed `preview` (line 620) is
already a valid, complete `AssignmentSetupPreviewResult` when there is no
template to validate; the call to `saveAssignmentSetup` was never necessary.

**Fix:** `ui/electron/main.ts:622` now returns the already-computed `preview`
instead of calling `saveAssignmentSetup(request)`.

**Renderer defense in depth, not a silent guard.** `AssignmentSetupPage.tsx`'s
`handlePreview` now checks `Array.isArray(nextPreview.files)` before trusting
the response; on failure it surfaces a plain-language error (`"Assignment
setup preview returned an unexpected response. Try again."`) through the
page's existing error-message mechanism and does not store the malformed
object into `preview` state. This is not "hiding" the malformed response --
the error is visible, plain-language, and per README section 2.5 -- it is the
alternative to either crashing or silently proceeding as if the response were
valid.

**General backstop:** a `RouteErrorBoundary` now wraps every route (`App.tsx`,
inside `HashRouter`, around `AppRoutes`), so any future render throw from any
routed screen shows a section-2.5 message instead of a blank screen, logs the
real error to the console (never swallowed), and resets when the route
changes (keyed by `location.pathname`) so navigating away recovers instead of
leaving the app stuck.

**A separate, real bug found while tracing this, reported rather than fixed
here (per this PR's explicit scope):** `DashboardPage.tsx`'s
`onOpenAssignment` handler navigates to the new assignment's detail route
immediately after firing `handleRefreshCourseFolder` without awaiting it. If
the dashboard cache refresh takes longer than the render that follows,
`AssignmentDetailRoute` will not find the brand-new assignment in its stale
cache and will show `RouteNotFound` for an assignment that was, in fact, just
created. Recorded as backlog item 29 -- a real, traced code path, not
reproduced under a jsdom timing race (mocked promises resolve too fast to
force it reliably in a test).

## Files Changed

- `ui/electron/main.ts` -- one-line fix: the `previewAssignmentSetup` IPC
  handler returns the already-computed preview instead of calling
  `saveAssignmentSetup` when there is no template repository to validate.
- `ui/src/assignment-setup/AssignmentSetupPage.tsx` -- `handlePreview` now
  validates that the IPC response has a `files` array before trusting it,
  surfacing a plain error instead of storing a malformed object into state.
- `ui/src/dashboard/RouteErrorBoundary.tsx` (new) -- the class-component error
  boundary (`RouteCrashBoundary`) plus a function wrapper
  (`RouteErrorBoundary`) that keys it by `location.pathname` so it resets on
  navigation.
- `ui/src/App.tsx` -- wraps `<AppRoutes />` in `<RouteErrorBoundary>`, inside
  `<HashRouter>` (so `useLocation`/`useNavigate` are available) and inside
  `<DashboardDataProvider>` (unaffected by the crash it guards against).
- `ui/src/test/routeTestUtils.tsx` -- `renderAtRoute` now wraps `<AppRoutes
/>` in `<RouteErrorBoundary>` too, matching production.
- `docs/ui-redesign/backlog.md` -- new item 29 (the refresh-race bug, above).

## Tests Added or Updated

- `ui/src/assignment-setup/AssignmentSetupPage.test.tsx` (+2):
  - **"shows a plain error instead of crashing when the preview response has
    no files array"** -- mocks `previewAssignmentSetup` to return exactly the
    malformed shape the real bug used to produce
    (`{status: "failure", writtenFiles: [], diagnostics: [...]}`, no
    `files`), clicks "Create assignment," and asserts the plain-language
    error renders and no dialog opens. **Confirmed this fails without the
    fix**: reverted the renderer's `Array.isArray` check locally and re-ran
    this test -- it failed with the exact reported crash, `TypeError: Cannot
read properties of undefined (reading 'map')` at
    `AssignmentSetupPage.tsx:634`, then restored the fix and reconfirmed the
    suite passes.
  - **"creates an assignment with no template repository through a full
    preview-confirm-save flow"** -- the test PR7-1 deferred ("the existing
    test only opens the modal, never confirms it"), specifically for the
    blank-template-repository path (the one that used to crash): fills the
    minimum required fields with both template fields left blank, clicks
    "Create assignment," confirms in the dialog, and asserts `onOpenAssignment`
    is called with the new assignment's file and slug, and that
    `saveAssignmentSetup` was called with `templateRepository: ""`.
- `ui/src/dashboard/RouteErrorBoundary.test.tsx` (new, +2): a synthetic
  always-throwing route proves the boundary renders the section 2.5 message
  (not a blank screen) and logs the real error via `console.error`; a second
  test clicks "Return to dashboard" and confirms the app recovers to a
  working screen rather than staying stuck on the fallback.
- **What could not be tested, and why:** the actual IPC contract bug lived in
  `ui/electron/main.ts`'s inline `ipcMain.handle` callback for
  `previewAssignmentSetup`. No test file in this repository exercises
  `main.ts`'s handler wiring directly (`main.test.ts` only tests one small
  guard function; nothing mocks `electron`'s `ipcMain`), and building that
  infrastructure from nothing is disproportionate to a one-line fix. The
  regression tests above instead prove the _renderer_ survives the exact
  malformed shape the bug produced, which is the level this repository's
  existing test seams support and is what actually stops the crash from
  reaching a user regardless of which future IPC handler might produce a
  similarly malformed response.

**Test count arithmetic (912 → 916, +4):** +2
(`AssignmentSetupPage.test.tsx`) + 2 (new `RouteErrorBoundary.test.tsx`) = 4.
Checked against the actual run: `916 passed (916)`.

## Result

Creating an assignment with no template repository (the simplest, most
common case, and the one the UI's own placeholder text invites) no longer
crashes the application. If any routed screen throws for any other reason in
the future, the app now shows a plain, on-brand error message with a way
back to the dashboard instead of a blank screen, and recovers as soon as the
user navigates away.

**What to re-test by hand** (this was found by hand, and should be confirmed
the same way): in a running Electron build, open a registered course folder,
click "New Assignment," fill in title/slug/term/at least one section, leave
both template repository fields blank, click "Create assignment," and
confirm in the dialog. The assignment detail screen for the new assignment
should open -- no white screen. Also worth a quick manual check: navigate to
a URL with a deliberately broken hash fragment while the app is mid-render of
something unusual, to see the new error boundary's fallback screen in a real
window (the automated test proves the mechanism; seeing the actual fallback
render once is still worth doing before calling this done).

Screenshot requirement remains unmeetable per backlog item 16 -- not
claimed.
