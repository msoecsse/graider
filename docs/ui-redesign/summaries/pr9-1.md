# PR9-1: apply preview, one page whose state changes

## Summary

Merged `ApplyPreviewPage.tsx`'s two panel sets (preview and result) into one
state-driven page, per README section 5.4. Concretely:

- **One plan table**, not a preview table and a separate result table. A new
  merge module (`applyPreviewMerge.ts`) joins each preview row with its apply
  result by student identity (group targets by group identity) into one
  `ApplyRowState`/`ApplyGroupRowState` per row. The table's Status/Reason
  cells read from the result once it exists, the preview before that — the
  same table updates in place; nothing is appended below it.
- **One summary sentence**, not ten counter boxes (five preview, five
  result). `getApplyPlanSummaryText` tallies directly from the same merged
  rows the table renders, so the sentence's counts agree with the rows shown
  by construction, not by cross-checking two separately-maintained sources.
- **One diagnostics region**, shown only when non-empty: `result.diagnostics`
  once apply has run, `preview.diagnostics` before that.
- **Design decision, made explicitly, as asked**: a shared row type with an
  optional result status (not two types with a shared presentation layer).
  Preview and result rows are joined once, up front, into `ApplyRowState`;
  every panel below (table, attention styling, summary tally) reads that one
  type. This kept the "Status column updates in place" requirement literal —
  there is one row object per student, and one of its fields changes.
- **`workflow_dispatch status`** → `Workflow dispatch status` (matches the
  wording already shipped for the same field on `AssignmentDetailPage.tsx`).
- **Reasons and statuses surviving the merge go through the existing
  `components/statusLabels.ts`.** No new label strings were written by hand;
  two genuinely new raw values the merge introduced (`blocked` and `pending`,
  from the group-mode apply result vocabulary — see "What I found," below)
  were added to that module's existing table, not inlined.

No backend or IPC change was needed.

## What I found (the target-counts investigation)

README section 5.4 says target counts don't currently agree with the rows
shown, and asks for the reason before touching either. Traced it to
`src/apply-preview/apply-preview-builder.ts:579`: **in group mode, the
backend returns `plan: { repositories: [], groupTargets: [...] }`** — the
per-student `repositories` array is always empty, while `plan.summary`'s
counts (`wouldCreateRepositories`, etc.) are computed from
`groupPlan.targets.length` — a _group_ count. The old `RepositorySummaryPanel`
showed that group count unconditionally, right above `RepositoryRowsPanel`,
which showed "No repository preview rows." for the exact same data — the
count was never wrong, it was being displayed next to the wrong table
(the individual-row table, when group mode has no individual rows at all).

The fix is the pairing, not the count, exactly as anticipated: the merged
page now renders one table appropriate to `preview.repositoryMode` (the
individual table or the group table, never both), and the one summary
sentence is tallied from whichever merged row array that table is showing.
This makes the mismatch structurally impossible rather than separately
corrected.

## A vocabulary I had to trace before merging group rows

Group-mode apply _result_ status (`ApplyResultGroupTarget.status`) is **not**
the same enum as individual-row result status
(`ApplyResultRepositoryStatus`). I initially assumed it was and nearly routed
it through the same formatter. Traced the real values to
`src/groups/group-target-executor.ts:32` (`"created" | "updated" | "failed"`)
and `src/cli/commands/apply.command.ts:213` (`"pending" | "blocked"` for the
preflight-only/guard-rejected paths that never reach execution). So group
result status is `created | updated | failed | pending | blocked` — a
superset that overlaps with the individual vocabulary on three values and
adds two of its own. `formatMergedGroupRowStatus` recognizes the shared three
via the existing `formatApplyResultRepositoryStatus`, and `blocked`/`pending`
are new entries in `components/statusLabels.ts` (with a `formatStatusLabel`
fallback for anything else, so a genuinely unrecognized value still renders
readably instead of crashing or going blank).

## Result

`ApplyPreviewPage.tsx` now renders one plan table, one summary sentence, and
one diagnostics region regardless of whether apply has run; running Apply
updates the same table and sentence in place rather than appending a second
copy below. `GradePreviewPage.tsx` (PR9-2) was not touched, as instructed —
it has the identical defect and can follow this exact pattern (merge module,
merged row type, one summary sentence tallied from the merged rows).

**What should look different in a running app:** where the page used to show
"Repository plan summary" (5 counter boxes) immediately above "Repository
rows" (a table), it now shows "Repository plan" with one sentence like "2
repositories will be created, 1 skipped, 1 blocked, 1 unknown." above the
same table. Clicking "Apply changes" no longer appends a second "Apply
Result Summary" panel, a second repository table, and a second "Diagnostics
/ blockers" panel below the first three — the existing sentence and table
update in place (a row that read "Would create" now reads "Created"), and
there is exactly one diagnostics panel, present only when there's something
to show. Group mode shows one "Group repositories" table instead of two.
The "workflow_dispatch status" label reads "Workflow dispatch status."
"Applied" and "Last refreshed" now show formatted dates instead of raw ISO
strings.

Screenshot requirement remains unmeetable per backlog item 16 — not claimed.
