# PR10-1: router

## Summary

Replaced `DashboardPage`'s nine nullable "selection" `useState` values --
the mechanism README section 4.1 exists to remove -- with a real router
(`react-router-dom` v6, `HashRouter`) and nine routes, four of which section
4.1 originally named and five of which are extensions this PR added so
every screen `DashboardPage` used to reach through selection state has a
real route. Every hand-placed "Back to dashboard" button and the grading
workspace's two "Back" buttons are gone, replaced by a `Breadcrumbs` trail
rendered above each routed screen; one exception was kept deliberately
(below).

**Library choice.** `HashRouter`, not `BrowserRouter`: production loads
through `window.loadFile` (`file://`), which has no server to resolve an
arbitrary path back to `index.html`, so `BrowserRouter` doesn't work.
`HashRouter` keeps the route in the URL fragment (`#/course/...`), which
`file://` serves unchanged; `MemoryRouter` would also run under `file://`
but gives up the one thing routing exists to add here -- a URL that
identifies where you are. None of the three gives a link that opens in
_another_ window or another faculty member's copy of the app; that needs a
registered custom protocol and an `open-url` handler in
`ui/electron/main.ts`, out of scope here (see Deferred and backlog item
26).

**The "one PR or three" question, resolved before writing code.** README
section 4.1's six-route table named three destinations with no real
component (a course page, the term setup wizard) or that weren't a screen
at all (publish review, which is `GradingPublishReviewPanel`, a state
inside the grading workspace) -- while five already-built screens
(`ApplyPreviewPage`, `GradePreviewPage`, `GradeStatusPage`,
`FacultyReportPage`, `AssignmentEditPage`) had no route at all, each still
reached only through a nullable selection state. Per direction: route all
nine real screens (the four original plus the five extensions), do not
build a course page or the setup wizard's route, and do not route publish
review. Section 4.1 has been corrected to match (see Documentation).

**Self-resolution, confirmed for all nine screens.** Every routed screen
resolves its own data from `:courseSlug`/`:termSlug`/`:assignment` alone,
via a shared `DashboardDataContext` (the dashboard's existing course-folder
and card cache, hoisted above the router) and two resolver hooks
(`useResolvedCourseFolder`, `useResolvedAssignmentSelection`) that turn
slugs into the same `AssignmentDetailSelection`/`CourseFolderRecord`
shapes the old click handlers built inline. No screen needed a new loader
or state threaded through the router to make this work.

## Files Changed

**New infrastructure:**

- `ui/src/dashboard/DashboardDataContext.tsx` -- `DashboardDataProvider`/
  `useDashboardData()`. Extracted, verbatim, `DashboardPage`'s course-folder
  load/refresh/remove logic and its aggregated-dashboard cache so any route
  can read it. Deliberately excludes dashboard-view-only state (course
  publish, faculty settings, search/sort/filter, GitHub auth) -- that stays
  local to `DashboardPage.tsx`.
- `ui/src/dashboard/dashboardResolvers.ts` -- pure slug-to-data functions:
  `findCombinedCard`, `findCourseFolderForCard`, `resolveCourseFolder`,
  `resolveAssignmentSelection` (returns the not-found reason for a missing
  card, a missing assignment, or a null `assignmentFile`), and
  `findAnyCardForFolder` (a folder can hold more than one card; used where
  only a folder, not a specific term, is in scope -- see below).
- `ui/src/dashboard/useRouteResolution.ts` -- `useResolvedCourseFolder()`/
  `useResolvedAssignmentSelection()`, each returning a
  `{status: "loading"} | {status: "not_found", reason} | {status: "ready",
value}` union so every route can tell "cache not loaded yet" apart from
  "genuinely doesn't exist."
- `ui/src/dashboard/RouteNotFound.tsx` -- `RouteNotFound` (README section
  2.5: one sentence, the reason, a "Return to dashboard" action) and
  `RouteLoading`.
- `ui/src/dashboard/breadcrumbHelpers.ts` / `ui/src/components/Breadcrumbs.tsx`
  -- the breadcrumb builder and the shared `<nav>` component. Rendered by
  each route wrapper _above_ the page's own `<main>`, not inside it -- a
  deliberate departure from extending `PageHeader` (backlog item 11). Only
  one of nine screens uses `PageHeader` at all; a wrapper-level component
  gives every routed screen the same trail without restructuring any
  page's internals or touching `PageHeader`.
- `ui/src/dashboard/routePaths.ts` -- one place building every route path
  and coercing a nullable slug to a route-safe string (`toRouteSlug`).
- `ui/src/AppRoutes.tsx` -- the `<Routes>` tree, split out of `App.tsx` so
  tests can mount the same routes inside a `MemoryRouter`.
- `ui/src/test/routeTestUtils.tsx` (new) -- `renderAtRoute`/
  `renderWithProviders`, the router-aware test helper used by every new
  test file below.

**Eight route wrappers** (one per routed screen; each resolves its slug(s),
renders `RouteLoading`/`RouteNotFound`/breadcrumbs + the real page, and
wires forward actions to `navigate()`):
`ui/src/assignment-detail/AssignmentDetailRoute.tsx`,
`ui/src/grading-workspace/GradingWorkspaceRoute.tsx` (redirects to the
grade-preview route if `window.graiderUI.prepareGradingWorkspace` isn't a
function, matching the old click-time feature check),
`ui/src/apply-preview/ApplyPreviewRoute.tsx`,
`ui/src/grade-preview/GradePreviewRoute.tsx`,
`ui/src/grade-status/GradeStatusRoute.tsx`,
`ui/src/faculty-report/FacultyReportRoute.tsx`,
`ui/src/assignment-edit/AssignmentEditRoute.tsx`,
`ui/src/roster-manager/RosterManagerRoute.tsx`.

**`ui/src/App.tsx`** -- now `DashboardDataProvider` > `HashRouter` >
`AppRoutes`.

**`ui/src/dashboard/DashboardPage.tsx`** -- consumes `useDashboardData()`;
the nine selection states and their early-return blocks are gone. Click
handlers `navigate()` instead of `setState()`. `CourseSetupPage` and
`AssignmentSetupPage` stay as local `useState`-gated views (folder-picker
driven, not slug-gated, per direction). Fixed one real bug this surfaced
(below).

**Removed "Back" buttons and their now-dead props**, replaced by
breadcrumbs: `AssignmentDetailPage.tsx` ("Back to dashboard", `onBack`),
`GradingWorkspacePage.tsx` (both "Back" buttons, `onBack`),
`ApplyPreviewPage.tsx` ("Back to assignment"/"Back to assignment detail"/
"Back to dashboard", `onBack`/`onBackToDashboard`),
`GradePreviewPage.tsx` (same three, same props),
`GradeStatusPage.tsx` ("Back to assignment detail", `onBack`),
`RosterManagerPage.tsx` ("Back to dashboard", `onBack`). Each page's own
type file (`applyPreviewTypes.ts`, `gradePreviewTypes.ts`,
`gradeStatusTypes.ts`, `assignmentDetailTypes.ts`) had the prop removed.
`ui/src/styles/globals.css`'s now-dead `.assignment-detail__back` rule was
removed.

**Kept deliberately:** `FacultyReportPage.tsx`'s "Back to grading status"
button and `onBackToGradeStatus` prop -- no breadcrumb crumb represents
grade status (the trail treats assignment detail as the report's
canonical parent), so it is the only way back there. Only
`onBackToAssignmentDetail` (redundant with the breadcrumb's assignment
crumb) was removed. `AssignmentEditPage.tsx`'s "Cancel" button is untouched
(a distinct semantic, not a "back" duplicate). `AssignmentSetupPage.tsx`
and `CourseSetupPage.tsx` keep their own "Back to dashboard" buttons --
not routed, no breadcrumb trail to replace them with.

**A real bug found and fixed, not just documented:**
`AssignmentSetupPage.tsx`'s `onOpenAssignment` callback always passes
`courseSlug: null` (it only has the bare `CourseFolderRecord`, not a
dashboard card, so it cannot know the slug). Navigating with that null
slug verbatim would have landed every "create assignment" flow on
`/course/unknown/...` -- a route no card ever matches -- showing
`RouteNotFound` instead of the new assignment. Fixed in
`DashboardPage.tsx`'s `onOpenAssignment` handler: resolves the real
`courseSlug` via `findAnyCardForFolder` against the already-loaded
dashboard cache (the folder was already on the dashboard before this flow
started, so its card -- and real slug -- already exists; no need to wait
for the refresh this flow also kicks off, which only needs to pick up the
new assignment). Caught by the new end-to-end test in `App.test.tsx`,
which failed against `RouteNotFound` before this fix.

**Dependency:** added `react-router-dom@^6.30.6` to `ui/package.json`.
`npm audit` in `ui/` shows a moderate advisory in this version (an open-
redirect issue in `<Link>`/`useNavigate` with attacker-controlled paths);
not applicable here since every route path in this app is built from
already-trusted local dashboard data, never from user-supplied or
remote input. `npm run audit` (root) does not audit `ui/` (separate
lockfile), so this does not affect CI's audit gate. v7 was not used --
it drops `HashRouter`'s v6 API shape and would have meant a second set of
decisions unrelated to this PR's scope.

## Result

Navigation across all nine routed screens is now real URLs under a
`HashRouter`, resolved from slugs alone via a shared dashboard-data cache,
with breadcrumbs in place of hand-placed "Back" buttons everywhere but one
deliberate exception. A real navigation bug (assignment setup landing on
`RouteNotFound` after creating an assignment) was found by the new
end-to-end test coverage and fixed, not merely documented.

**What should look different in a running app:** every routed screen now
shows a breadcrumb trail (Dashboard › Course · Term › ... ) above its
content instead of a "Back to dashboard"/"Back to assignment detail"
button; the address bar's hash changes as you navigate and back/forward
work; visiting `/course/<bad-slug>/...` shows a plain "This page could not
be found" message with a reason and a way back, never a blank screen.
Reloading the app while on any of these routes reopens the same screen
(HashRouter survives a reload the way in-memory selection state never
could) — this was not previously possible at all.

Screenshot requirement remains unmeetable per backlog item 16 -- not
claimed.
