# PR10-3: split GradingWorkspacePage

## Summary

Split `GradingWorkspacePage.tsx` (3,915 lines, the largest component in the
app) into 11 new presentational child components, each in its own file with
its own test file, following the PR10-2 pattern where the boundary was clean
and leaving code inline, with reasons, where it was not. The main file is
now 2,975 lines — a 24% reduction, smaller than PR10-2's 42% on
`AssignmentDetailPage.tsx`, for a structural reason explained below, not
because fewer boundaries existed. All twelve pre-existing grading-workspace
test files pass completely unchanged; nothing needed to move or be rewritten
for a non-location reason.

**Why the reduction is smaller than PR10-2's, honestly stated up front:**
`AssignmentDetailPage.tsx`'s bulk was mostly JSX (a large "Advanced details"
disclosure of mostly-static panels). `GradingWorkspacePage.tsx`'s bulk is
mostly behavior: roughly 2,080 of its 3,915 lines are state declarations,
effects, and handler functions (mutation orchestration, autosave, the
keyboard-shortcut dispatcher, publish-review polling) that this task's scope
— a presentational split, no behavior change — does not touch and PR10-2's
own conclusion says belongs in the container. The JSX return block itself
(originally ~1,296 lines) is what got extracted, and it came out almost
entirely: after extraction only one deliberately-inline block of comparable
size remains, explained below. A smaller top-line number with honest
boundaries beats a larger one with bad ones, per the task's own instruction.

## What was found, and how it was grouped

**Matched cleanly to README §5.1's named regions, extracted as new
components:** `GradingProgressHeader` (header: title, progress bar, `Publish
N reports`, cheat-sheet button), `GradingFooterHintBar` (static footer hint
bar, zero props), `GradingKeyboardCheatSheetModal` (the `?` shortcut
cheat-sheet dialog), `GradingStudentListPane` (left pane: filter pills,
student list, Previous/Next ungraded), `GradingSubmissionViewerPane` (centre
pane: the lazy-loaded `MonacoSourceViewer` + `Suspense` boundary, moved
whole, plus the Add Comment affordance), `GradingScorePanel` (the rubric
score bars — the cleanest single-prop extraction in the file),
`GradingAppliedCommentsPanel` (applied-comments list + its delete
confirmation), `GradingManualAdjustmentsPanel` (manual-adjustments list,
add/edit form, and delete confirmation), `GradingWorkflowRepairPanel`
(single- and bulk-workflow-repair controls, including both of their
`ConfirmationWithPreviewModal` call sites, moved together as a unit — see
below).

**The comment library, split into two rather than one:** README §5.1 names
"Comment library" as one region, but the underlying JSX was ~279 lines
touching ~17 distinct pieces of state — the exact "15-prop component"
shape the task warns against. It decomposed cleanly into two genuinely
separate concerns that happened to share a `<section>`: `GradingCommentEditorForm`
(the add/edit form — moved with its own `AddCommentEditorState`/
`EditCommentEditorState`/`CommentEditorState` types, ~8 props) and
`GradingCommentLibraryBrowser` (search, tag filter, matching list, Apply —
~11 props). The thin `<section>` wrapper (heading + the shared
`gradingMutationError` banner, ~15 lines) stays in the page, composing both
as siblings — matching PR10-2's precedent of keeping pure composition
inline rather than adding a layer with no JSX of its own.

**Left inline, with reasons, per "if a section has no clean boundary, say
so and leave it":** the right pane's status/score/publish cluster (student
status line, Mark Complete button + its confirmation, Preview Report +
Publish/Republish buttons + the report-publication `ConfirmationWithPreviewModal`

- the report-preview modal — roughly 195 lines). This block reads 15+
  distinct, tightly-coupled pieces of page state (`snapshot`, `currentEffectiveStatus`,
  `gradingMutationStudentId`, `gradingMutationBlockedStudents`, `publishReviewRunning`,
  `reportPreview`, `reportPublicationStudentId`, `reportPublicationNotice`,
  `reportPublicationConfirmation`, `markCompleteConfirmation`, and five
  handlers) and is rendered in exactly one place. This is the same shape as
  PR10-2's template-sync confirmation flow, left inline there for the same
  reason: extracting it would not shrink anything, it would move the same
  props one file over. The `discardDraftPrompt` modal (the fourth
  `ConfirmationWithPreviewModal` call site, the only one with a real
  `onSuccess`) is six lines around an already-shared component, used once —
  no boundary worth drawing, same as PR10-2's delete-assignment dialog.

**Module-scope helper functions** (`label`, `sourceTargetLabel`,
`sourceLocationLabel`, `signedAmount`, `STUDENT_FILTER_EMPTY_MESSAGE`) are
pure string/lookup transforms, not components — they stayed in the page and
are passed down as props to whichever new component renders their output,
the same pattern PR10-2 used for its page-local derivation helpers.

## The three named differences from PR10-2's pattern

**1. Test-file naming convention: left as-is, not aligned.**
`GradingWorkspaceCommitHistory.test.tsx` and `GradingWorkspaceEvidencePanel.test.tsx`
(covering the pre-existing `GradingCommitHistoryPanel`/`GradingEvidencePanel`)
both mount the full `GradingWorkspacePage` and mock `window.graiderUI` —
confirmed by reading their imports before deciding. They are integration
tests of the page's wiring to those panels, not unit tests of the panels in
isolation, so a workspace-scoped name is the accurate one; renaming them to
`GradingCommitHistoryPanel.test.tsx` would misrepresent what they test. This
is why `MonacoSourceViewer.test.tsx` — a true unit test that imports and
renders the component directly — already carries the PR10-2-style
component name and needed no change. My own 11 new test files use the
PR10-2 convention (`GradingScorePanel.test.tsx`, etc.) because they _are_
genuine per-component unit tests: each imports its component directly and
renders it with mock props, no page mount, no `window.graiderUI`.

**2. Feature-organized tests: nothing moved.** All seven pre-existing
feature test files (`GradingWorkspacePage`, `Publication`, `BulkPublication`,
`WorkflowRepair`, `KeyboardShortcuts`, `SiblingPanels`, `CommitHistory`,
`EvidencePanel`) mount the full page and assert on behavior that spans
multiple panels, handlers, and `window.graiderUI` mocks — the unsaved-draft
guard across student switches, keyboard shortcuts closing over the whole
handler surface, publish-review polling, cross-panel state agreement. Unlike
PR10-2, which found three tests genuinely isolated to one panel's own
rendering (`AssignmentFactsPanel`), no test case here asserted purely on one
newly-extracted component with no cross-component or data-fetching
entanglement. Judgment: leave all seven exactly where they are. This is why
all twelve pre-existing test files (2,845+341+346+276+423+530+424+... lines)
pass **completely unchanged** — the strongest available evidence the split
changed no behavior.

**3. Cross-cutting state, checked before touching anything:**

- **Keyboard shortcuts.** The dispatcher (one `useEffect`, no dependency
  array, by design) closes over nearly the entire handler surface of the
  component — `goToNextUngradedStudent`, `openAddCommentEditor`,
  `markCompleteAndAdvance`, `applyReusableCommentByPosition`, etc. It is not
  extractable as its own component; it stayed exactly where it was, in the
  page, unchanged. `GradingWorkspaceKeyboardShortcuts.test.tsx` ran in
  isolation 3 times before this change (18/18, 18/18, 18/18) and 3 times
  after (18/18, 18/18, 18/18) — identical, no new intermittent failure.
  (One correction to the task's own framing: backlog item 7's flake is
  recorded as **Resolved** as of the `asyncUtilTimeout` fix, not open — this
  matches backlog item 27's caution about task-prompt descriptions drifting
  from the document they cite. It doesn't change anything here; the test
  passed clean regardless.)
- **The four `ConfirmationWithPreviewModal` call sites.** `discardDraftPrompt`
  (real `onSuccess`) — left inline. The report-publication modal (no-op
  `onSuccess`, paired with `reportPublicationNotice`) — left inline, inside
  the status/score/publish cluster described above; the handler and the
  notice state it writes to were never separated because the whole cluster
  stayed together. The bulk- and single-workflow-repair modals (both no-op
  `onSuccess`, paired with `bulkWorkflowRepairResult`/`workflowRepairNotice`
  respectively) — moved **together as one unit** into
  `GradingWorkflowRepairPanel`, so each handler still travels with the
  notice state it writes to; only their location changed, not their
  pairing.
- **`gradingMutationStudents`** (backlog item 19's ref-backed set). Checked
  every read/write site before starting: it is set and read only inside
  `runGradingMutation`, `confirmPublishReport`, `runPublishReview`,
  `flushPendingViewState`, and `scheduleViewStateSave` — five handler
  functions, none of which this refactor touched. It has **zero**
  references inside the JSX that moved. The state it's compared against for
  item 19's race (`gradingMutationStudentId`, read by every mutation
  button's `disabled`) did move — but only as a plain prop value, passed
  down unchanged to whichever new component renders that button, read at
  the same point in the same render as before. Item 19's analysis is
  unaffected and needs no update: the single flag and the ref-backed set it
  warns about are exactly as separate, and exactly as un-tested, as they
  were before this PR. (Distinct from `gradingMutationStudents`:
  `gradingMutationBlockedStudents`, a _different_ ref used pervasively in
  per-button disabled checks throughout the old JSX, is the one this
  refactor threads through — as an `isStudentMutationBlocked(studentId)`
  callback prop, created fresh each render in the page and passed to
  children, so `.current` is still read live at click time, not captured
  stale.)

## The publish route question

**Not now claimable, and this split didn't change that.** PR10-1 left
`/…/:assignment/publish` unrouted because `GradingPublishReviewPanel` is
state-driven (`publishReviewOpen`), not a route — but `GradingPublishReviewPanel`
was _already_ its own extracted component before PR10-3 (a prior PR). This
split didn't touch it, its call site, or the `publishReviewOpen`/
`cancelPublishReview`/`openPublishReview` state machine around it at all.
What would make the route claimable is turning that local boolean into a
URL-driven mode — a routing change, not a component-boundary change — and
that remains out of scope here, not attempted.

## Result

`GradingWorkspacePage.tsx` is a container: state, effects, IPC calls, the
keyboard-shortcut dispatcher, and one deliberately-inline, tightly-coupled
JSX cluster, composing 11 new presentational children plus the four
components already extracted in a prior PR (`GradingCommitHistoryPanel`,
`GradingEvidencePanel`, `GradingPublishReviewPanel`, `MonacoSourceViewer`).
Every extracted component has its own test file. No DOM output changed for
any state the app can be in — proven by running all twelve pre-existing
test files unchanged against the fully-split code, and by an exact
structural diff (headings, roles, aria attributes, class names) between the
old file and the new one.

**What to check by hand**, since this refactor has no visible output of its
own and this is the screen faculty use most: open a grading workspace with
students in several statuses and confirm — the header's progress bar and
`Publish N reports` button; the `?` cheat sheet; the left pane's filter
pills, student selection, and Previous/Next ungraded (including the
unsaved-draft guard when switching away from an edited comment or
adjustment); the source viewer and its Add Comment affordance after
selecting a range; Mark Complete and its confirmation; Preview Report;
Publish/Republish this student's report and its confirmation; the rubric
score bars; editing and deleting an applied comment; adding, editing, and
deleting a manual adjustment; automated checks and commit history (both
untouched, but downstream of the same panes); single- and bulk-workflow
repair and both their confirmations; the comment-library add/edit form
(including the Source/General target radio and its coupling to the
selected source range) and applying a library comment by search or tag.
Exercise every keyboard shortcut in the cheat sheet, not just `J`/`K`/`?`,
since the dispatcher closes over the full handler surface and a stale
closure would show up as a shortcut silently doing nothing rather than as a
crash.

Screenshot requirement remains unmeetable per backlog item 16 — not
claimed.
