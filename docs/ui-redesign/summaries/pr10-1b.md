# PR10-1b: assignment save reports the wrong error

## Summary

Fixed the two defects in `AssignmentSetupPage.tsx`'s `handleSave` that
`9b02459` left in place, traced which failure mode actually fires for the
reported repro ("test"/"t2", not already present), and fixed that root
cause too, since it reproduces the exact symptom and is the same class of
bug PR10-1a already fixed in the sibling handler.

**Defect 1 -- the real reason was constructed and discarded.**
`handleSave`'s `else` branch built `new Error(result.diagnostics.map(...).join(" "))` from the backend's actual explanation, then a bare `catch` one line
later replaced it with the generic `"Unable to save assignment.yml."` before
it ever reached the user. Fixed: the IPC call itself is now the only thing
in a `try`/`finally` (no `catch` -- a genuine failure to reach the main
process now propagates with its own real message), and the result is handled
explicitly afterward. A failure result's diagnostics are joined and thrown
directly; an empty diagnostics list says so ("Assignment setup failed, and
no reason was reported.") instead of substituting the old generic sentence.

**Defect 2 -- the `try` was too wide.** It wrapped the save call, the
`writtenFiles[0]` check, and `onOpenAssignment(...)` (the router navigation
callback PR10-1 rewired) under one `catch`, so a navigation failure _after_ a
successful save was reported as a save failure. Fixed: `onOpenAssignment` now
runs in its own `try`/`catch`, reached only once `result.status === "success"`
is already established, producing its own distinct message ("The assignment
was saved, but opening it failed: ...") that can never be confused with a
save failure.

**Which failure mode actually fires for "test"/"t2":** traced
`ui/electron/main.ts`'s `saveAssignmentSetup` IPC handler. Unlike the
`previewAssignmentSetup` handler (fixed in PR10-1a to skip
`validateTemplateRepository` entirely when the template repository field is
blank), the **save** handler still calls `validateTemplateRepository`
unconditionally. `normalizeTemplateRepository("")` returns `null` (an empty
string never matches `REPOSITORY_PATTERN`), and `validateTemplateRepository`
returns `{valid: false, diagnostics: [{message: "Template repository value
must be in owner/repo form or a GitHub repository URL."}]}` the moment
`repository === null` -- before any GitHub or token check runs, deterministic
regardless of auth state. So **every save of an assignment with no template
repository fails** with that diagnostic, for a field the UI's own
placeholder invites leaving blank ("Leave both template fields blank to
omit"). This is the same root cause class as PR10-1a, in the same file, on
the sibling handler that PR10-1a did not touch. Assuming the hand-test left
the template fields blank (the simplest, most common configuration, and the
one PR10-1a's own repro used) -- confirmed as the actual failure mode by
static trace, not by reproducing it live. **The save is genuinely failing
here; this is not the `DashboardPage.tsx:378` navigation race (backlog item 29) -- that race produces `RouteNotFound` after a successful save, not a
save-time diagnostic before any file is written.**

Fixed: `main.ts`'s `saveAssignmentSetup` handler now skips
`validateTemplateRepository` when the template repository field is blank,
mirroring the preview handler exactly.

**The sibling, checked as asked.** `handlePreview`'s `catch` is bare
(`catch { setMessage("Unable to prepare the assignment setup preview."); }`)
but is **not the same defect**: nothing inside its `try` throws a
diagnostic-carrying error for the catch to discard -- the one diagnostics
path (`nextPreview.status !== "ready"`) already calls `setMessage(...)`
directly, never `throw`. The only thing this catch can see is a genuine,
unexpected failure to reach the main process at all (e.g. `main.ts`'s own
`isAssignmentSetupRequest` guard throwing). Fixed anyway for consistency: the
catch now preserves that error's own `.message` when present, falling back
to the generic sentence only when there truly is nothing more specific.

**`AssignmentEditPage.tsx`, checked rather than fixed.** Its `save()`
function does **not** share defect 1: there is no `catch` block at all
around its `try`/`finally`, so `throw new Error(result.diagnostics...)`
(line 155) propagates to `ConfirmationWithPreviewModal`'s own catch
unmodified -- the real diagnostic reaches the user today. It shares a much
weaker version of defect 2: `onSaved()` is called inside the same `try` as
the save call, so if it threw, that would be reported through the same path
as a save failure (though, unlike the fixed bug here, without losing the
message -- the modal's catch preserves `error.message` either way). Not
fixed here, per this PR's scope: reported for whoever next touches this
file, alongside the pre-existing gap that it has no test file at all
(backlog item 17).

## Result

A failing assignment save now shows the backend's actual reason (or says
plainly that none was given), never a generic substitute. A save that
succeeds but whose subsequent navigation fails is reported as exactly that,
not as a save failure -- and, since the save result is no longer discarded,
a user in that situation cannot accidentally trigger a duplicate write by
re-confirming what looks like a failed save. Creating an assignment with no
template repository (the case reported by hand) now succeeds end to end,
since the underlying validation asymmetry between preview and save is gone.

**What to re-test by hand:** create an assignment with a title and slug not
already present in the course, leave both template fields blank, confirm --
should succeed and open the new assignment's detail screen. Separately,
worth trying a save against a slug that already has an `assignment.yml`
(without checking "replace existing") to see the real conflict diagnostic
rather than a generic message.

Screenshot requirement remains unmeetable per backlog item 16 -- not
claimed.
