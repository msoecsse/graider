# PR12-1: settable heading id on PageHeader

## Summary

Added an optional `titleId` prop to `PageHeaderProps` and wired it to the
rendered `<h1>`'s `id` attribute. This closes the gap step-12-feasibility.md
§6 and backlog item 11 identified: `PageHeader`'s heading had no settable
`id`, so a caller's `<main aria-labelledby="...">` landmark could not point
at it. `AssignmentDetailPage.tsx` — the only current `PageHeader` caller —
worked around this by putting `aria-label={title}` directly on its `<main>`
instead of using `aria-labelledby` + heading id.

Prop naming and shape were chosen to match the codebase's existing
convention, not invented: `ConfirmDialog.tsx` and
`ConfirmationWithPreviewModal.tsx` already use a `titleId` variable
(generated internally with `useId()`) for the same purpose — pairing a
`aria-labelledby` landmark with a heading's `id`. `PageHeader`'s heading id
has to come from the caller instead of being generated internally, because
the landmark that needs it (`<main>`) lives outside `PageHeader` in the
screen component, not inside it — so `titleId` is a settable prop here
rather than an internal `useId()` call. This also matches the dominant
pattern across the app: a survey of every screen's top-level `<main>`
(`grep -rn "aria-labelledby=\"[a-z-]*title\"|<main" ui/src/*/*.tsx`) found
9 of 10 routed screens use `aria-labelledby="<screen>-title"` paired with an
explicit `<h1 id="<screen>-title">`; `AssignmentDetailPage.tsx`'s
`aria-label={title}` is the lone outlier, and existed only because this
capability was missing.

## Files Changed

- `ui/src/components/PageHeader.tsx` — added `titleId?: string` to
  `PageHeaderProps`; the `<h1>` now renders `id={titleId}`. When omitted,
  `id` is `undefined` and React emits no attribute, so existing callers
  (`AssignmentDetailPage.tsx`) are unaffected — confirmed by running its
  existing tests unchanged and by the diff, which touches only two lines
  inside `PageHeader.tsx` (add the prop, set the id).

## Tests Added or Updated

Both new, both in `ui/src/components/PageHeader.test.tsx`. No existing test
was changed.

- `sets the heading id from titleId so an external landmark can resolve it`
  — renders `PageHeader` inside a `<main aria-labelledby="page-title">` and
  asserts `getByRole("main", { name: "Lab 02" })` resolves, which only
  passes if the browser's accessible-name computation actually walks
  `aria-labelledby` to the heading's text — i.e. it tests the association,
  not just that the `id` attribute is present. It separately asserts the
  heading carries `id="page-title"` and the `<main>` carries the matching
  `aria-labelledby`.
- `omits the heading id when titleId is not supplied` — asserts the heading
  has no `id` attribute at all when the prop is left out.

## Result

Done. `PageHeaderProps` now accepts an optional `titleId`, which sets the
rendered heading's `id`. Existing callers and tests are unaffected —
confirmed by running the full suite (all 139 UI test files, including
`AssignmentDetailPage`'s own tests) and by the two-line production diff.
This unblocks `RosterManagerPage`'s planned `PageHeader` migration (PR12-5)
without forcing it to give up its `aria-labelledby="roster-manager-title"`
landmark pairing, and closes the heading-id half of backlog item 11.

**How this could be verified with a screen reader / accessibility
inspector**, beyond the automated test: open a screen using `PageHeader`
with `titleId` set (once PR12-5 lands) in VoiceOver (macOS) or the
Chrome DevTools Accessibility pane. In DevTools, inspect the `<main>`
element's "Computed Properties" — "Name" should read the heading text
("Manage rosters", not blank or the raw `id` string), which is exactly what
`aria-labelledby` resolving correctly produces. In VoiceOver, navigating by
landmark (VO+U → Landmarks) to the page's main region should announce that
same heading text as the region's name, not "main" alone. Today, before
this PR, `RosterManagerPage.tsx` already does this correctly by hand
(`aria-labelledby="roster-manager-title"` + `<h1 id="roster-manager-title">`
outside `PageHeader`); the behavior this PR enables is identical, just
reachable through `PageHeader` instead of a hand-written `<h1>`.

Definition of done (README §7), scoped to a shared-component prop addition
rather than a screen: no disabled button/generic string, no raw status
