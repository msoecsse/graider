# PR12-2: shared roster parse/validate/diff module

## Summary

Added a new, pure-TypeScript module in `src/roster/` with the four concerns
step-12-feasibility.md §4 and backlog item 36 asked for: CSV parsing,
column matching (the seam for item 33), validation, and a per-row diff
against a baseline. No call site was converted — all four existing parsers
(`src/roster/roster-loader.ts` + `src/io/csv.ts`,
`ui/electron/courseSetupService.ts`, `ui/electron/rosterManagerService.ts`,
`ui/src/roster-manager/RosterManagerPage.tsx`) are unchanged and untouched.

### Where it lives, and why

`src/roster/`, alongside `roster-loader.ts`, `roster-validation.ts`,
`roster-normalization.ts`, and `roster-models.ts` — the module extends that
existing home rather than starting a new one.

This repository has one established pattern for getting `src/` logic to
`ui/electron/` without `ui/electron/` importing ESM `src/` TypeScript
directly: `ui/scripts/build-template-sync.mjs` compiles specific
`src/**/*-context.ts` files into standalone CommonJS bundles under
`ui/dist-electron/*.cjs` (fifteen of these exist today, e.g.
`facultyScopeBackend.cjs` from `src/faculty/faculty-scope-context.ts`), and
a matching `ui/electron/*Service.ts` `require()`s the built bundle. This is
what "ui/electron/ declares its own types rather than importing across the
require()-loaded .cjs boundary" refers to, and it is why `ui/electron/`'s
`tsconfig.node.json` scopes `rootDir`/`include` to `electron/**/*.ts` only
— it never has a source file living outside that directory.

Putting the new module in `src/roster/` is what lets it fit that pattern
without inventing a new one: `src/` consumers (the CLI/grading path) import
it directly, exactly as `roster-loader.ts` already imports
`roster-validation.ts`. `ui/electron/` consumers, when a future PR converts
`courseSetupService.ts` or `rosterManagerService.ts`, follow the same
`-context.ts` + `build-template-sync.mjs` entry + `require()` path every
other shared backend capability already uses — no new mechanism, no
tsconfig changes, and (per "Migrate nothing yet") no entry added to
`build-template-sync.mjs` in this PR, since nothing calls it yet.

The renderer (`ui/src/roster-manager/RosterManagerPage.tsx`) is the one
consumer this doesn't fully resolve today. Its CSV-upload preview
(`parseUploadedRoster`) runs client-side, synchronously, on a browser
`File`, before any IPC round trip — there's no backend call in that path to
attach validation to. The module has zero Node dependencies (no `fs`,
`path`, or other built-ins) specifically so it's _reachable_ by the
renderer, but making it actually reachable means either widening Vite's
dev-server `fs.allow` (and, more basically, deciding whether the renderer
importing across the `ui/` → repo-root package boundary is something this
codebase wants at all — it doesn't do it anywhere today) or routing the
upload preview through a new IPC call instead. That's a real decision with
its own tradeoffs, out of scope for a "no UI change" PR, and left for
whichever future PR converts `RosterManagerPage.tsx`'s CSV upload (most
naturally PR12-5, the screen rebuild, since that's also when the diff this
module produces gets its first caller).

### Diff semantics — decisions made explicitly, per the prompt's request

- **Row identity**: `studentId`, trimmed and lowercased for comparison only
  (the stored value is untouched). This matches the key
  `roster-validation.ts`'s duplicate detection already uses.
  Consequence, accepted deliberately: if a row's `studentId` itself
  changes between baseline and current, it is not recognized as "the same
  row, renamed" — it reads as one row dropped (old id) and one row added
  (new id). Any single-field identity key has this property; `studentId`
  is the roster's existing natural key, so it's the one used. Covered by
  `roster-diff.test.ts`'s "treats a student_id edit as one dropped row
  plus one added row".
- **Status change (e.g. active → dropped) is `"changed"`, not
  `"dropped"`.** `"dropped"` means the row itself is absent from the
  current set — a student removed from the roster entirely — not a status
  field edit. This matches §5.6's amber/red split (amber = field edit,
  red = row gone) and keeps the red category meaning what the confirm
  dialog's copy already promises it means.
- **A row in the baseline but absent from the current upload is
  `"dropped"`, not ignored.** The feasibility pass confirmed dropping a
  student today doesn't touch their repository or reports, so surfacing it
  (not silently discarding the row) is safe and lets faculty catch an
  accidental omission in a re-uploaded CSV before saving.
- The diff's `rows` array carries only `added`/`dropped`/`changed` entries
  (not `unchanged` ones) — `unchangedCount` is reported as a count only.
  Nothing in the described UI use (`UnsavedChangesBar`'s message, the
  confirm dialog's row list) needs unchanged row bodies.

### Validation — reused, not reimplemented

`parseAndValidateRosterCsv` calls `validateRequiredColumns`,
`createMissingRequiredValueDiagnostic`, `validateRosterStatus`,
`validateRosterSection`, `validateGithubUsername` (all from
`roster-validation.ts`) and `normalizeStudentId`, `normalizeGithubUsername`,
`normalizeRosterStatus` (from `roster-normalization.ts`) unmodified. Only
the row-by-row orchestration loop is new, and it exists because
`roster-loader.ts`'s equivalent (`loadSectionRoster`) is tied to reading a
file off disk; this version takes CSV text directly so it can run against
an in-memory upload or a live-edited table, matching `roster-loader.ts`'s
loop closely enough that a future PR could plausibly rebase
`roster-loader.ts` onto this module instead of the reverse (not attempted
here — out of scope).

One rule intentionally **not** included at this level:
`validateRosterDuplicates`. `roster-loader.ts` doesn't call it inside
`loadSectionRoster` either — it's applied one level up, in
`loadTermRosters`, across every section's combined student list.
`parseAndValidateRosterCsv` matches `loadSectionRoster`'s single-CSV scope,
so duplicate detection stays a caller concern, same as it already is for
the CLI path. A caller validating one CSV in isolation (as
`rosterManagerService.ts`'s `validateRows` does today) should call
`validateRosterDuplicates` itself alongside this module when it migrates.

### The strengthened CSV parser

`roster-shared-csv.ts` wraps `src/io/csv.ts`'s existing `parseCsv` — the
strongest of the four current parsers' tokenizers (correct quote/escaped-
quote/embedded-comma handling, CRLF-tolerant) — and adds the one capability
none of the four have: stripping a leading UTF-8 byte-order mark. `csv.ts`
itself is untouched, so `roster-loader.ts`'s current behavior is
unaffected. Multi-line quoted fields (a value containing a literal newline)
remain unsupported, same as all four current parsers, since none of them
handle it and the prompt's test list didn't ask for it — noted under
Deferred, not silently added.

### The column-matching seam (item 33)

`matchRosterColumnsByExactName` is the only `RosterColumnMatcher`
implemented. It reproduces `roster-loader.ts`'s existing
`getColumnIndexes` behavior: order-independent, tolerant of extra
unrecognized columns (so the legacy seven-column header with
`email`/`first_name`/`last_name` already works, same as it does for the
CLI path today). Item 33's best-effort/user-editable header mapping is a
second `RosterColumnMatcher` implementation plugged in later via the same
`(headers) => RosterColumnIndexes` seam — nothing about parse, validate, or
diff needs to change for it.

## Result

Done. One new module (`src/roster/roster-shared*.ts` + `roster-diff.ts` +
`roster-column-matching.ts`) provides parse, the column-matching seam,
validation (reusing `roster-validation.ts`/`roster-normalization.ts`
unmodified), and diff, with 29 new tests and no change to any of the four
existing parsers. All requested validation commands pass.

Also, per the prompt's one allowed exception: **`rosterManagerService.ts`'s
weaker validation looks like an actual defect, not a deliberate
relaxation.** Nothing in the code, comments, or docs suggests the gaps
were intentional — it reads as an independently hand-rolled parser that
never matched `roster-loader.ts`'s rigor, which is exactly backlog item
36's problem. Concretely, compared to `roster-loader.ts`:

- `getRosterForSection` requires the header line to equal
  `ROSTER_HEADERS.join(",")` or `LEGACY_ROSTER_HEADERS.join(",")`
  **exactly**, in that exact order — a roster with the same four columns
  in a different order is rejected outright, where `roster-loader.ts`
  accepts any order.
- `validateRows` lowercases `status` before checking it but never
  lowercases `studentId` or `githubUsername`, so `"jones"` and `"JONES"`
  are not caught as duplicate student IDs here, where
  `roster-loader.ts`'s normalization step would catch it.
- Diagnostics are untyped `{message: string}` strings with no `code`,
  losing the structured-diagnostic parity the CLI path has.

Recommend fixing this by migrating `rosterManagerService.ts`'s roster-CSV
path onto `parseAndValidateRosterCsv` (plus its own
`validateRosterDuplicates` call, per the note above) rather than patching
the existing parser in place. The natural point to do that is PR12-5 (the
roster manager screen rebuild), which already has to touch this file to
wire the confirm dialog to this PR's diff — not urgent standalone, per
backlog item 33's own note that no new rosters are being created until
next term.
