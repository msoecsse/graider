# PR10-2: split AssignmentDetailPage

## Summary

Split `AssignmentDetailPage.tsx` (2,722 lines -- README section 4.2's number
of 2,482 was stale, consistent with backlog item 27's pattern of this
document's inventories drifting from the code; corrected here by observation,
not by editing section 4.2 itself, since this task's scope is the split, not
another documentation correction) into 15 presentational child components,
each in its own file with its own test file, following the
`AssignmentDetailStudentTable.tsx` (PR6b-3) precedent. The main file is now
1,580 lines -- a 42% reduction -- and holds exactly what a route-level
container should: state, effects, IPC calls, and JSX composition. No behavior
change; the existing test file passed unchanged after the entire extraction,
before a single test was moved.

## What was found, and how it was grouped

**Already its own component:** `AssignmentDetailStudentTable.tsx` (PR6b-3).
Untouched.

**Module-scope functions already isolated from the render, just living in
the same file** (the majority of the split -- these already had clean,
single-purpose prop signatures; extracting them was a pure relocation):
`AssignmentFactsPanel`, `RosterPanel`, `TemplatePanel`, `GradingPanel`,
`GradeWorkflowPanel`, `StudentReportsPanel`, `DiagnosticsPanel`,
`ReadinessPanel`, `TemplateSyncResultsPanel`, `GradeStatusSummaryPanel`,
`StudentRepositoryAccessPagePanel`, `StudentRepositoryAccessPagePublishPanel`
(the "access-page panel" and its own confirmation/publish flow named in the
prompt -- two related but distinct panels, not one). Four small, genuinely
shared display primitives used across several of these panels --
`DetailItem`, `StatusItem`, `CopyButton`, `DiagnosticEntry` -- moved together
into `AssignmentDetailPrimitives.tsx` rather than each panel importing them
from wherever they happened to land; `getRepositoryShortName` and
`getCopyStateText` went there too since they are used by more than one
panel.

**Inline JSX with no name of its own, extracted as new components:**
`GroupRepositoryModePanel` (repository mode / group membership CSV, nested
inside Advanced details -- the prompt's own example of what to expect) and
`RepositoryDownloadResultsPanel` (the repository-download results block,
also previously inline).

**Left in place, with reasons, per "if a section doesn't have a clean
boundary, say so and leave it":**

- **The overflow menu's group/item construction** (`overflowGroups`) is
  data, not JSX -- an array of menu descriptors closing over ~6 pieces of
  page state and several handlers. It fits `<OverflowMenu>`, an already-
  shared component; there is no additional JSX layer here to extract.
- **The template-sync confirmation flow** (`ConfirmationWithPreviewModal`
  invocation, its title/summary/confirmation-word branching for
  single-vs-bulk sync, the paired `OperationStatusBar`, and the "unavailable"
  guidance banner) reads or writes eleven distinct pieces of page state
  (`templateSyncAvailability`, `templateSyncTarget`, `isTemplateSyncModalOpen`,
  `isExecutingTemplateSync`, `templateSyncProgress`, `templateSyncError`,
  `templateSyncNotApplicable`, `isSingleTemplateSync`,
  `templateSyncStatusDetail`, `title`, `executeTemplateSync`) and is
  rendered in exactly one place. Extracting it would not shrink anything --
  it would move the same eleven props one file over, which is exactly the
  "200-line component with fifteen props" the prompt warns against. Left
  inline.
- **The delete-assignment `ConfirmDialog`** is six lines of props around an
  already-shared component, used once. No boundary worth drawing.
- **`buildTechnicalDetailsItems`** and **`buildAssignmentLifecycleSteps`**
  are pure derivation functions (JSON in, a plain array out), not
  components -- there is no JSX to extract, so they stayed as page-local
  helpers feeding the already-shared `TechnicalDetails`/`LifecycleStrip`
  components.

**Found, not fixed:** `CollapsibleDiagnosticsPanel`, a second, unused
diagnostics-rendering function sitting next to the real (and actually
rendered) `DiagnosticsPanel`. It has no call site anywhere in the file --
dead code, not a variant used somewhere I missed. Per "do not fix unrelated
bugs, report them instead" and this being a pure refactor, it was left
exactly where it was (not extracted, since extracting dead code serves no
one) and is reported here rather than deleted.

## Tests Added or Updated

**Ran `AssignmentDetailPage.test.tsx` completely unchanged after the full
component extraction, before moving or adding a single test: all 53 tests
passed.** This is the strongest evidence available that the split changed
no behavior -- confirmed again by running the entire UI suite (925/925)
against the extracted-but-not-yet-test-split code.

**Moved (not rewritten) -- 3 tests**, from `AssignmentDetailPage.test.tsx`
to `AssignmentFactsPanel.test.tsx`: "renders the assignment facts Template
row as a link to the repository, not a raw path", "shows a plain
placeholder, not a broken link, when no template repository is
configured", and "shows the Grading fact in plain language, combining
enabled state and mode". Same input data, same assertions; only the render
harness changed, from mounting the full page through `window.graiderUI`
mocks to mounting `AssignmentFactsPanel` directly with an equivalent
already-normalized `detail` object. These were the cleanest candidates:
each asserted purely on this one panel's own rendering, with no page-level
data-fetching or cross-component wiring mixed in.

**Not moved, and why:** the remaining 50 tests in
`AssignmentDetailPage.test.tsx` are genuine integration tests -- they
exercise the template-sync confirmation flow, the delete flow, workflow
fetching/editing, group config saving, access-page generation/publishing,
and copy-button wiring across multiple panels at once. Moving these would
mean either reproducing page-level orchestration inside a single
component's test (testing something the component doesn't own) or
thinning the assertion to fit the new home, which is a rewrite, not a
move. Per "if a test needs changing for a reason other than location, stop
and say why" -- the reason these stay is that they are not, in fact, about
one component's location; they are about the page's wiring, which still
lives in the page. They are unchanged.

**New tests added for each extracted component's own rendering contract**
(41 new test cases total, in the 15 new `.test.tsx` files listed above,
including the 3 moved ones): each covers the component's main rendering
path and at least one edge case (null/empty data, a disabled/hidden
branch, a callback firing with the right argument) directly through props,
without going through `window.graiderUI` or the page's data-fetching
pipeline.

**Test count arithmetic (925 → 963, +38):** -3 (moved out of
`AssignmentDetailPage.test.tsx`) + 41 (new files, including the 3 moved
in) = +38. Checked against the actual run: `963 passed (963)`.

`AssignmentDetailPage.tsx` is now a container: state, effects, and IPC calls,
composing 15 presentational children plus the pre-existing
`AssignmentDetailStudentTable`. Every extracted component has its own test
file. No DOM output changed for any state the app can be in -- proven by
running the untouched 53-test page suite against the fully split code before
any test was moved.

**What to check by hand, since this refactor has no visible output of its
