# PR10-1c: three false-signal bugs in the create/delete flow

## Summary

Three independent bugs, found by hand-testing `a4ebb6e`, fixed on their own
merits. None of the three involved a broken operation — each one made the UI
report something untrue about an operation that actually worked.

### 1. "Page could not be found" flashes before a new assignment opens (backlog item 29)

Confirmed the traced-but-unreproduced race from PR10-1b's backlog item 29 is
now directly visible: `DashboardPage.tsx`'s `onOpenAssignment` fires
`handleRefreshCourseFolder` and navigates without awaiting it, so
`AssignmentDetailRoute` resolves against a cache that doesn't have the new
assignment yet.

Fixed without a timeout and without awaiting the refresh before navigating
(the alternative the original prompt offered): `useResolvedAssignmentSelection`
(`useRouteResolution.ts`) now checks whether the assignment's own card's
folder is currently being refreshed
(`refreshingId === card.sourceFolderId`, exposed by `DashboardDataContext`,
or a refresh-all in flight) before concluding "not found." A missing
assignment in a folder that is mid-refresh now resolves to `loading`
(`RouteLoading`) instead of `not_found` (`RouteNotFound`) -- exactly the
distinction the type's own comment says exists for this. The route goes
straight from loading to the real assignment once the refresh lands, with
no error flash between.

`useResolvedCourseFolder` (the roster route's resolver, structurally
identical) was deliberately left alone: `handleOpenRosterManager` already
refuses to navigate to a folder with no card yet (it shows an error message
instead), so there is no live path that reaches this same race for roster --
fixing it too would be extending the change beyond what any current
behavior needs.

Backlog item 29 updated to **Resolved**.

### 2. False "Student repository updates unavailable" on template-less assignments

Traced what repository template-sync actually does before deciding, per the
prompt's instruction not to soften the message and leave the logic as is.
`assignment-template-sync-context.ts`'s `template_required` blocker gates a
feature that syncs a student's _already-created_ repository toward the
**template's latest commit** -- `resolveCurrentTemplateCommitSha` calls
`client.getTemplateRepository(...)` and the whole operation is meaningless
without a template repository to sync toward. Unlike the two bugs PR10-1a
and PR10-1b fixed (both about whether _creating_ a repository needs a
template, where blank is a valid "no template" choice), this gate is not
encoding the same wrong assumption -- it is a genuine, structural
requirement of a different feature. **Decision: the gate is correct; the
presentation was wrong.** A feature that does not apply to a correctly
configured assignment is not a failure to explain (README sections 2.1 and
2.5) -- it should not appear at all.

Fixed: `AssignmentDetailPage.tsx` now hides both the "Update Student
Repositories" secondary action and the "Student repository updates
unavailable" banner specifically when `blocker.code === "template_required"`.
Every other blocker code (a real, actionable problem on an assignment that
_does_ have a template -- a missing manifest, an unresolvable template
repository, and so on) still shows the button (disabled, as before) and the
banner unchanged.

**Checked whether the same assumption appears anywhere else, as asked:**

- `ui/electron/main.ts`'s `previewAssignmentEdit` and `saveAssignmentEdit`
  handlers already skip template validation when the field is blank -- no
  bug there; these were apparently the correct pattern the setup-flow
  handlers PR10-1a/1b fixed should have matched from the start.
- `templateWorkflowService.ts`'s "not_configured" status (grading workflow
  generation, a related but separate feature) does carry a similar
  "template required" message, but its one consumer,
  `AssignmentDetailPage.tsx`'s `GradeWorkflowPanel`, already renders it as a
  quiet `detail-panel__note` next to a disabled button, not a failure
  banner, and the disabled button already means the message is never even
  fetched for a template-less assignment in the first place. No visible bug
  found there; not changed.

### 3. Deleting an assignment leaves it in the dashboard list

`AssignmentDetailRoute.tsx`'s `onDeleted` only navigated to the dashboard;
nothing refreshed the affected course folder's cache, so the deleted
assignment stayed listed until a manual refresh.

**Ordering, chosen deliberately:** refresh-then-navigate, not
navigate-then-refresh. The dashboard has no placeholder for "this row is
being removed" the way a not-yet-loaded row can show a loading state (bug
1's fix) -- navigating first would show the just-deleted assignment still
listed until the refresh landed, then have it vanish a moment later. That is
a smaller version of the same "stale-then-corrects-itself" flash bug 1 was
about, right after a destructive action the user just deliberately
confirmed. Awaiting the refresh before navigating means the dashboard is
already correct the instant it renders -- one IPC round trip's worth of
extra wait on a screen the user already expects some latency from (they
just typed a confirmation word and clicked a destructive action).

Fixed: `AssignmentDetailRoute.tsx`'s `onDeleted` now calls
`handleRefreshCourseFolder(selection.courseFolderId)` and navigates to the
dashboard only once that resolves.

## Files Changed

- `ui/src/dashboard/useRouteResolution.ts` -- `useResolvedAssignmentSelection`
  distinguishes a missing-but-refreshing assignment (`loading`) from a
  genuinely missing one (`not_found`).
- `ui/src/assignment-detail/AssignmentDetailPage.tsx` -- hides the "Update
  Student Repositories" action and its unavailability banner specifically
  for the `template_required` blocker.
- `ui/src/assignment-detail/AssignmentDetailRoute.tsx` -- `onDeleted` awaits
  a refresh of the affected course folder before navigating to the
  dashboard.

  actually shipped.

## Result

Creating an assignment no longer shows a "not found" error before landing on
its detail page. A template-less assignment's detail page no longer shows a
permanent, misleading "unavailable" failure banner for a feature that
structurally does not apply to it. Deleting an assignment removes it from
the dashboard list immediately, with no manual refresh required.
